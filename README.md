# 聊天记录自动备份 (Chat Auto Backup)

SillyTavern UI 扩展。按楼层数自动导出角色卡聊天记录，每个角色卡、每个聊天独立计数、独立文件夹。

目标版本：SillyTavern 1.18.0（本机 D:\ST\SillyTavern），`minimum_client_version` 声明 1.14.0。

## 楼层标准（1.1.3 定稿）

文件名与计数里的「楼层数」= **最后一条消息的数组索引**（`mesid`，与界面楼号同一套编号）：

- 依据（已查 ST 1.18.0 源码）：`redisplayChat` 对**全部**消息渲染并赋 `mesid = 数组下标`；
  `is_system` 楼同样被渲染，核心 CSS 也没有任何隐藏 `[is_system]` 的规则
  → **隐藏楼就是真实楼层，占楼号**
- 1.1.1/1.1.2 曾用「最后一条非隐藏消息的索引」当楼号，对 MVU 卡会算错，已废弃
- 1.1.0 及之前用 `chat.length`（总条数），天然比最后一条索引大 1
- 如果你的界面显示与面板仍差 N 楼（个别卡/主题会自己隐藏 system 楼），
  在设置项「楼号校准」填 `-N` 即可，不用改代码、不用硬编码 +2
- **为什么不能恒定 +2**：差值不是常量。实测两个聊天：
  演员版 50 条 / 48 条隐藏楼（差 2），歌手版 439 条 / 427 条隐藏楼（差 0）。
  隐藏楼由卡片脚本随时注入，数量会变，硬编码必然在某天错位

## 导出契约（唯一口径，勿再改）

**文件名里的 N = 楼层索引 `#N`（0 起），文件内容 = 从 `#0` 到 `#N` 的完整快照，共 N+1 条消息。**

| 文件名 | 内容范围 | 消息条数 |
|---|---|---|
| `角色卡——USER——50` | `#0` ~ `#50` | **51 条** |
| `角色卡——USER——100` | `#0` ~ `#100` | **101 条** |
| `角色卡——USER——150` | `#0` ~ `#150` | **151 条** |
| `角色卡——USER——200` | `#0` ~ `#200` | **201 条** |

即「每隔 50 层导出」= 在 `#50 / #100 / #150 / #200 …` 各出一份累积快照，
不是 51-100 这种增量片段。自动导出同理：到达 `#437` 时文件名 `——437`，内容 438 条。

> 用户视角锚点：界面楼层索引 `#` 后面跟的数字 = 文件名里的数字。

## 1.1.4 修正：导出文件缺元数据表头（回导入少一楼层）

`context.chat` 是**不含**元数据的（加载时 `data.shift()` 已剥离首行），而 `/api/chats/import`
以首行当表头校验并原样拷贝、加载时又剥一次 → 前端序列化的 jsonl 首条消息会被当成表头吃掉，
**回导入后整体少一条、所有楼号 -1**（表现：`——50` 的文件打开最后一层是 #49）。

修复：前端导出的 jsonl 首行补 `{ user_name, character_name, chat_metadata }` 表头，
结构与酒馆原生导出一致。往返验证：51 行（无表头）→ 导入后 50 条 #49；
52 行（有表头）→ 导入后 51 条 **#50** ✓

## 切片规则（1.1.3 修正）

- 回溯文件 `——N` = 索引 `[0, N]` 共 N+1 条，精确切片
- 「切片带隐藏楼」设置项（默认 **0**）控制是否额外吞并截止楼之后的连续隐藏楼
- 1.1.2 及之前该吞并无上限：星光旅途这类 MVU 卡会连续注入几百条隐藏楼，
  导致「要 50 楼、实际切出 428 条」——即每个文件都是整档。已加上限并硬校验

## 需求对照

| # | 需求 | 实现 |
|---|------|------|
| 1 | 记录角色卡聊天楼层 | 楼层 = 酒馆界面楼号（mesid，0 起，开场白 #0），取最后一条可见消息的索引；脚本隐藏楼不占楼号 |
| 2 | 达到楼层计数后导出 | `当前楼层 - 上次导出楼层 >= 间隔` 时触发导出 |
| 3 | 可配置每 X 楼导出一次 | 设置项「导出间隔（楼）」，默认 50，可 1 起任意填 |
| 4 | 文件名 `角色卡名称——USER名称——楼层数` | 严格按此格式（下载模式可并入聊天名，可关） |
| 5 | 不同角色卡计数隔离 | 计数键 `char:<characterId>:<chatId>` / `group:<groupId>:<chatId>`，各记各的 |
| 6 | 不同角色卡分文件夹 | `<根目录>/<角色卡名>/<角色卡名.创建日期>/`，自动建目录 |
| + | 同一角色卡不同聊天也分文件夹 | 同上，聊天层文件夹名默认 `角色卡名.2026.9.1`（取首楼时间） |

## 安装

1. 复制整个 `chat-autobackup` 目录到 `SillyTavern/public/scripts/extensions/third-party/`
2. 重启 SillyTavern，扩展管理里启用「聊天记录自动备份」
3. 扩展设置面板 → 选「选择目录」授权备份根目录（一次性，句柄存 IndexedDB）
4. 设置导出间隔，开始聊天

## 设置项

| 项 | 默认 | 说明 |
|----|------|------|
| 启用自动备份 | 开 | 总开关 |
| 导出间隔（楼） | 50 | 每新增多少楼层导出一次 |
| 普通备份保留上限 | 10 份 | 间隔为 1～9 时触发滚动保留（全部模式每整十楼永久保留；仅 AI 模式每 10 轮 AI 回复永久保留）。授权目录内每个聊天单独滚动清理普通备份 |
| 导出格式 | JSONL | JSONL 可回导入酒馆；TXT 便于阅读 |
| 数据源（JSONL） | 本地直出 | 本地内存直出 `Blob` 零拷贝写盘；可选切回服务端导出 |
| 计数方式 | 全部楼层 | 「仅 AI 楼层」= 按非开场白 AI 回复轮次计数，每 N 轮备份一次（文件名仍为界面楼号） |
| 空回拦截 | 开 | 最新楼为空白或空思维链外壳时延后备份，等重新生成有效内容后再导 |
| 重生成 / Swipe 自动更新 | 开 | 授权目录模式下在当前里程碑楼层重生成/Swipe/编辑时防抖原地覆写（进入下楼自动定稿） |
| 保存方式 | 写入授权目录 | 目录写入按卡分文件夹；或浏览器下载 |
| 备份根目录 | 未授权 | 授权后静默写盘，未授权自动回退下载 |
| 目录层级 | 角色卡 / 聊天记录 | 另有 仅角色卡 / 仅聊天记录 / 平铺 |
| 聊天文件夹命名 | 角色卡名.创建日期 | 另有 聊天文件名 / 导出时间戳 |
| 下载文件名含聊天名 | 开 | 仅影响下载模式 |
| 楼号校准 | 0 | 界面楼号比面板小 N 就填 `-N`；等价于你自己掌控的「恒定偏移」 |
| 切片带隐藏楼 | 0 | 0 = 精确切片；>0 时截止楼后最多额外带几条连续隐藏楼（上限 50） |
| 同名文件 | 追加序号 | 追加 (2)(3) 保留历史版本；可选覆盖 |
| 导出后提示 | 开 | toastr 提示 |

面板还提供：立即备份、回溯备份历史段落、忽略历史空档、重置本卡计数、清理无效计数、斜杠命令 `/cabackup`（`/cabackup interval=30` 改间隔）。

例如间隔设为 3 楼、上限设为 2 份，聊到第 21 楼，目录内会留下第 **10、20** 楼的永久备份，以及最近的第 **18、21** 楼普通备份。整十楼与常规间隔重合时只自动生成一份。间隔为 10 楼及以上时，按原间隔保留全部备份。

自动备份、手动备份和回溯备份共用上限。清理顺序取决于文件的备份时间，原地更新同一个文件仍算一份。在高频模式下调低上限后，扩展会清理当前授权根目录中各聊天超额的普通备份。滚动清理从升级后写入并登记的文件开始，旧版存档继续保留。浏览器下载的文件由用户自行管理。

## 回溯备份历史段落（1.1.0）

在一张已经超过间隔的老卡上首次启用插件时，点「回溯备份历史段落（N 段）」按间隔补齐过往楼层。

- 当前 438 楼、间隔 50、从未备份 → 生成 8 个文件：**50 / 100 / 150 / 200 / 250 / 300 / 350 / 400**
- 每个文件都是**累积切片**：`——50` 含第 1-50 楼，`——100` 含第 1-100 楼，不是 51-100 这种增量片段
- 只补到「当前楼层向下取整的间隔倍数」（438 → 400），不满一段的尾巴（401-438）等下次自动备份
- 已回溯到 300 楼时再点 → 只补 350 / 400，不重复生成
- 回溯后基线抬到最后一段（400），下次自动备份发生在 450 楼
- 段数 > 60 会先弹确认，避免一次生成几百个文件
- 不想补历史：点「忽略历史空档」标记为已备份，面板不再提示

## 实现要点

- 计数隔离：首次见到某计数键时把基线对齐到向下取整的间隔倍数（438/50 → 400），不补导历史也不狂导出；删楼层导致回退时按间隔重对齐基线，不破坏里程碑节奏。「仅 AI 楼层」模式（1.3.1 起）基于非开场白 AI 回复轮次做映射计算，跳过用户楼和隐藏楼但文件名与基线仍对应真实界面楼号。
- 空回与重生成处理（1.2.0）：触发导出前校验正文（含剥离空 `<think>` / 注释壳），空回直接跳过且不推进基线；若在当前刚备份的里程碑楼层重生成、Swipe 或编辑，FSA 模式下 3.5 秒防抖原地覆写原文件，直接推进到下一楼则立即切片定稿上一里程碑。
- 回溯导出只能走前端增量序列化（服务端 `/api/chats/export` 不支持切片），1.2.0 起采用 `O(N)` 增量缓冲 + `Blob` 分块写入并分片让出主线程，避免重复 `JSON.stringify` 卡死界面。
- 导出内容：JSONL 默认本地内存直出 `Blob`（省去 `saveChat` 与服务端二次 JSON 转义开销），也支持切回 `POST /api/chats/export`（TXT 整档默认走服务端），失败自动回退本地序列化。
- 落盘：File System Access API 句柄存 IndexedDB，递归 `getDirectoryHandle(..., {create:true})` 自动建目录；无授权或浏览器不支持时回退 Blob 下载。
- 不使用 `hooks.activate`，APP_READY 后自举，兼容 1.14.0+。
- 所有外部字符串经 `textContent` 注入 DOM。

## 已知限制（需真机验收）

- 自动多次下载在部分浏览器会弹「允许多文件下载」确认，建议用目录写入模式。
- File System Access API 需 Chrome / Edge 等 Chromium 内核，且需在 localhost 或 HTTPS 下使用。
- 目录句柄权限在浏览器重启后可能需要重新授权一次。
- 尚未在真实酒馆中跑过完整触发链路（安装、刷新、切卡、导出、禁用清理）— 需用户实测确认。
- 回溯备份基于当前已加载到内存的 `context.chat`，若聊天是分页加载的（移动端），需先加载完整历史再回溯。
